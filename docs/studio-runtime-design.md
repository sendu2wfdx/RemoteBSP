# RemoteBSP Studio 与上位机运行时边界

## 定位

RemoteBSP 采用与 Klipper 相近的“Linux 负责策略、MCU 负责确定性执行”分工，但
面向通用机电设备。上位机产品不应是一台同时承担配置、构建、实时调度和浏览器
会话的单体程序，而应分成三个边界稳定的部分：

1. **RemoteBSP Studio**：设备工程、资源映射、固件生成、构建、烧录与回读；
2. **RemoteBSP Runtime**：类似 Moonraker 的常驻服务，管理节点、作业、权限、
   遥测和运行时 API；
3. **RemoteBSP Web**：类似 Fluidd 的可替换 Web UI，只调用 Runtime API，不直接
   访问 SocketCAN、USB 或 Studio 构建目录。

Studio 是部署控制面，Runtime 是设备运行控制面。两者可以由同一安装包提供，但
进程、权限和 API 必须分开。

## 职责边界

| 能力 | Studio | Runtime | Web UI |
|---|---|---|---|
| 选择板型、引脚、AF、DMA | 负责 | 只读已部署清单 | 展示或跳转 Studio |
| 生成、构建板卡专用固件 | 负责 | 不负责 | 仅展示任务状态 |
| ST-Link/Katapult 烧录与回读 | 负责 | 提供维护窗口和节点重连 | 发起经授权的部署作业 |
| 节点发现、资源目录、租约 | 不直接访问 | 负责，复用 `toolbusd` | 调用 Runtime API |
| 运动作业、GPIO/UART/SPI/I2C | 不执行实时操作 | 负责调度与审计 | 提交意图并显示状态 |
| 高频遥测、事件与告警 | 只用于部署诊断 | 负责采集、限流和保留 | WebSocket/SSE 订阅 |
| 设备业务协议与运动规划 | 不负责 | 插件或上层应用负责 | 提供交互界面 |

任何浏览器请求都不能直接变成 CAN 帧。Runtime 先完成身份校验、资源授权、参数
校验、幂等和限流，再通过 `libremotebsp`/`toolbusd` 访问节点。紧急停止可有专用
高优先级入口，但仍必须经过固定、安全、可审计的服务路径。

## 工程、部署和运行态模型

三类数据需要明确分离：

- **工程文档**：用户期望的板型和静态资源映射，带 `schema_version`；
- **部署记录**：规范工程哈希、固件配置哈希、固件哈希、工具链和目标节点身份；
- **运行态快照**：在线状态、队列、故障、计数器和遥测时间戳，不写回工程。

工程哈希基于 UTF-8、键排序和固定缩进的规范 JSON，因此不受编辑器排版和对象
键顺序影响。固件配置哈希基于最终 `.config`。多个工程可能生成同一固件配置，
所以两个哈希都要保留：前者回答“用户部署了哪个工程”，后者回答“实际构建了
哪套固件配置”。

当前工程 schema 为 v1。没有 `schema_version` 的早期草案按 v0 处理，只补充 v1
版本字段，并在 API 和构建记录中留下迁移说明；高于当前版本的工程必须拒绝读取，
不能猜测降级。后续每次迁移都应是纯函数，并配套固定输入、固定输出的回归测试。

## 第一阶段本地 API

现有 `gui/server.py` 仍是本地 Studio 原型，只监听本机且不承担真实运行时控制：

- `GET /api/project/target`：声明 API、工程 schema、构建和运行时能力；
- `POST /api/project/inspect`：迁移、校验并返回工程哈希与资源摘要，不产生文件；
- `POST /api/project/generate`：返回相同工程元数据及 Kconfig 和配置哈希；
- `POST /api/project/build`：构建并归档迁移后的规范工程、固件和构建记录；
- `GET /api/state`：目前只读演示或 Mock 快照，不是 Runtime API。

第一阶段不增加网络认证，也不把该本地服务暴露到局域网。未来 Runtime 应使用独立
的版本前缀（例如 `/api/v1/`），将命令请求与长连接事件流分开，并为写操作提供
请求 ID、幂等结果、操作者、目标节点、超时和审计记录。

## 后续实施顺序

1. 定义 Runtime 的节点、资源、作业、告警四类只读模型，并从 Mock 提供数据；
2. 将 Studio 的烧录建模为有状态部署作业，完成镜像、目标、回读三方核对；
3. 增加 Runtime 写命令和资源租约，先覆盖 GPIO、UART 和运动安全停机；
4. 增加事件流、遥测降采样和历史查询，再开发独立 Web UI；
5. 最后提供插件边界，承载设备协议、运动学和面向具体设备的业务逻辑。

在没有实体板环境时，所有接口先以 Mock 契约测试验证。实板测试由统一环境完成，
测试结果必须区分“Mock 通过”“交叉编译通过”和“实板通过”。
