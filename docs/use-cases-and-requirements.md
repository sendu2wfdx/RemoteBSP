# 使用场景与系统需求

## 设备拓扑

系统采用主从结构：

- 主机由 Linux 上位机和一块本地工具板组成。
- 从机由一块或多块远端工具板组成。
- 所有工具板统一连接到 CAN 或 CAN-FD 总线。
- 同一系统中允许同时存在不同功能、不同资源和不同 MCU 的工具板。

Linux 上位机负责统一发现、管理和调度工具板资源。应用程序应像使用本地资源
一样使用远端 GPIO、UART、SPI、I2C、ADC、PWM、定时器和存储资源，不直接
感知 CAN 分片、节点地址和请求重试。

## 核心运行要求

### 故障隔离

- 单个工具板离线不能阻塞其他节点。
- 单个工具板响应变慢不能拖延无关请求。
- 单个资源异常不能使整块工具板或整个系统停止服务。
- 例如某块板的一个 UART 异常时，同一板上的其他 UART 和其他板卡仍应工作。
- 所有请求必须有独立超时、取消、重试和错误状态。
- 节点级状态和资源级状态必须分开维护。

### 实时性

- CAN 接收、重组和事件分发不能被某个 IPC 客户端或慢请求阻塞。
- 每个节点和资源需要独立队列，避免队头阻塞。
- 高频事件和普通请求响应应采用不同优先级。
- 控制类短请求不能长期排在大块 UART 数据之后。
- 缓冲区必须有明确容量和溢出策略，禁止无限增长。

### 多节点

- 节点使用稳定硬件 UUID 识别。
- 运行时节点 ID 由主机分配。
- 同一总线允许多个不同型号节点并存。
- 节点发现必须返回资源清单，而不只返回一个固定能力位图。
- 节点掉线后，其未完成请求应独立失败，不能清空其他节点请求。

## UART 使用场景

单块工具板可能同时提供 8 个或更多 UART。UART 来源可能包括：

- MCU 原生 UART。
- SPI 转 UART 扩展芯片。
- 其他能够实现相同 UART 语义的板级资源提供器。

Linux 上位机不应区分 UART 的物理实现方式。原生 UART 和扩展 UART 应使用
相同对象模型、配置格式、读写接口、状态和错误码。

### UART 配置

每个 UART 至少需要描述：

- 逻辑资源 ID。
- 端口名称或索引。
- 波特率范围。
- 支持的数据位、停止位和奇偶校验。
- RX/TX 缓冲容量。
- 当前运行状态。
- 物理实现类型可作为诊断信息，但不参与应用层接口选择。

### UART 数据路径

UART 不能只依赖请求式短读取。应同时支持：

- 轮询读取，适用于 Modbus 等主站轮询协议。
- 异步 RX 事件，适用于 GPS 等持续输出设备。
- 分块读取和写入。
- 每端口独立 RX/TX 环形缓冲。
- 缓冲高水位、溢出、帧错误、奇偶校验错误和过载事件。
- 每端口独立流量控制，禁止一个高流量端口占满整个 CAN 总线。

对于 GPS 等持续数据流，应允许为端口设置：

- 事件触发阈值。
- 最大事件分块长度。
- 最大上报频率。
- 总线带宽配额或优先级。

## 资源抽象边界

原始原则“MCU 不包含设备专用驱动”需要进一步明确。

MCU 仍然禁止包含：

- Modbus 协议。
- GPS 协议解析。
- 传感器驱动。
- 阀门协议。
- 厂商业务协议。
- Linux 应用逻辑。

但工具板固件允许包含板级资源适配器，例如：

- MCU 原生 UART 适配器。
- SPI 转 UART 芯片适配器。
- 外部 GPIO 扩展器适配器。
- 板载 ADC、PWM 或存储控制器适配器。

这些适配器只能把板载硬件转换为统一的原子资源接口，不得理解连接在 UART、
SPI 或 I2C 后面的业务设备协议。

例如 SPI 转 UART 芯片由固件中的板级适配器管理后，对上位机暴露为普通 UART
资源。该 SPI 控制器被声明为内部占用资源，不再作为通用 SPI 暴露给 Linux。

## 资源清单

固定能力位图只能表示“是否具有某类能力”，无法表示 8 个 UART、每个端口的
缓冲和限制。当前协议已经实现：

```text
RESOURCE_ENUM
RESOURCE_DESCRIBE
RESOURCE_STATUS
RESOURCE_RESET
```

资源描述至少包含：

- 资源类型。
- 逻辑资源 ID。
- 功能和配置能力。
- 依赖关系。
- 是否被板级功能占用。
- 最大传输单元或单次操作长度。
- 缓冲容量。
- 健康状态。

应用层通过逻辑资源 ID 使用资源，不使用 MCU 外设编号或 SPI 芯片寄存器编号。

## 健康监控

系统需要两级健康状态。

节点级状态：

- 在线。
- 性能下降。
- 离线。
- 重启或会话变化。

资源级状态：

- 正常。
- 忙。
- 缓冲高水位。
- RX 溢出。
- TX 超时。
- 硬件错误。
- 已禁用。
- 正在恢复。

资源异常应产生事件，并支持对单个资源执行复位。复位一个 UART 不应重启整个
节点。

## MCU 与固件规划

后续目标 MCU 可以包括 STM32G431，但不属于当前 Phase 1。

固件阶段需要：

- 基于 Kconfig/menuconfig 的功能配置。
- 按板型选择 MCU、引脚、原生外设和板级扩展器。
- 配置每类资源数量和缓冲大小。
- 配置 CAN 或 CAN-FD 参数。
- 配置板级资源依赖和占用关系。
- 生成可重复的固件构建配置。

Bootloader 可以评估 canboot，用于通过 CAN 更新工具板固件。Bootloader、
固件升级协议、回滚和镜像签名应作为独立阶段设计。

## 硬件 ID

工具板需要硬件 ID 识别功能，初步方案是使用 ADC 采样电阻网络。

固件启动时应：

1. 多次采样硬件 ID ADC。
2. 进行滤波并计算稳定值。
3. 按配置的阈值表映射到硬件型号或修订版本。
4. 对落在阈值边界或未知区间的值报告错误。
5. 将识别结果加入节点信息和诊断信息。

硬件 ID 不能替代 UUID：

- UUID 标识具体某一块板卡。
- 硬件 ID 标识板卡型号或硬件修订。
- 运行时节点 ID 用于当前总线寻址。

## 当前阶段约束

当前 Phase 1 继续只实现 Linux 主机、Mock MCU、Classical CAN、CAN-FD 和
SocketCAN。STM32G431、canboot、menuconfig 和 ADC 硬件 ID 先记录为后续阶段，
不在当前代码中提前实现。
