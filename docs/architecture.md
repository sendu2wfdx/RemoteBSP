# Remote BSP 架构

详细设备拓扑、故障隔离、多 UART、板级资源适配、固件配置和硬件 ID 需求见
[使用场景与系统需求](use-cases-and-requirements.md)。
后续多轴步进、限位联锁、TMC 通信和运行时资源清单见
[智能实时资源与多轴运动控制设计](intelligent-motion-resources.md)。

Remote BSP 的目标是让 Linux 负责设备协议和业务逻辑，让远端 MCU 只执行
通用、原子的硬件操作。

预期数据路径如下：

```text
应用程序 -> libremotebsp -> toolbusd -> 远程协议
        -> 分片与重组 -> LinkTransport
        -> SocketCAN / libusb / Mock USB -> 远程核心
```

各层必须保持清晰边界：

- 协议层定义数据包及其线格式，不了解 CAN、CAN-FD、SocketCAN 或具体传输。
- 分片层根据传输 MTU 拆分和重组完整协议包，不直接收发 CAN 帧。
- 传输层负责帧收发，并向上层报告 MTU 和工作模式。
- 远程核心负责校验和分发通用硬件请求。
- BSP 层负责执行原子硬件操作。

## 第一步：协议数据包编解码

版本 1 的协议头固定为 24 字节。所有多字节整数均使用小端线序：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 1 | 协议版本 |
| 1 | 1 | 消息类型 |
| 2 | 2 | 命令 |
| 4 | 4 | 会话 ID |
| 8 | 4 | 请求 ID |
| 12 | 4 | 对象 ID |
| 16 | 2 |载荷长度 |
| 18 | 2 | 标志 |
| 20 | 4 | CRC-32 |

CRC 使用 IEEE CRC-32 算法，覆盖协议头的字节 0 至 19 以及全部载荷，不包含
CRC 字段本身。

一个完整编码数据包（含协议头）最大为 2048 字节。版本 1 解码器会拒绝未知
版本，避免错误解释不兼容的数据格式。

## 第二步：分片与重组

分片层接收完整编码数据包和 MTU，不依赖 SocketCAN、libusb 或具体链路。
Classical CAN 使用 8 字节 MTU，CAN-FD 和 USB 第一版使用 64 字节逻辑 MTU。

每个分片具有 5 字节的小端序头：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 2 | 传输 ID |
| 2 | 2 | 从零开始的分片序号 |
| 4 | 1 | 位 0 为 FIRST、位 1 为 LAST、位 2～7 为真实分片载荷长度 |

重组时单独传入发送方标识 `stream_id`，避免不同节点使用相同传输 ID 时发生
冲突。长度字段可表示 1～63 字节，本协议在 64 字节 MTU 下最多使用 59 字节。
真实 CAN-FD 控制器只能发送离散 DLC 长度，传输层会把帧补零到 8、12、16、
20、24、32、48 或 64 字节；解码器依据长度字段剥离并严格校验零填充。

Linux 重组器允许乱序重组，可以检测完全重复和内容冲突的分片。固定内存 MCU
实现利用 CAN 对同一发送方保持顺序的特性按序接收，并允许多个传输槽交错；
重复片会进行内容比较。两端都拒绝非法序号、非零填充以及超过 2048 字节的
数据，长时间不活动的传输会在超时后清理。

传输 ID 由每个发送端统一分配，响应、心跳和异步事件共用同一个出站计数器，
不能直接复用对端请求的传输 ID。节点尚未分配地址时，发现响应和临时心跳会
共用临时 CAN ID；统一计数器可避免两类消息在同一重组流中撞号。

## 第三步：通用链路与 CAN/USB 适配器

`LinkTransport` 是 toolbusd 和 Mock MCU 唯一依赖的链路接口，提供：

- `send()`：发送一条带逻辑路由号的链路帧。
- `receive()`：按指定超时接收一条链路帧。
- `mtu()`：返回当前模式的载荷上限。
- `capabilities()`：返回链路类型、可靠性、顺序性和标称速度。

`SocketCanTransport` 是 Linux 实现。Classical CAN 使用 `struct can_frame`，
CAN-FD 使用 `struct canfd_frame`。帧转换代码负责校验 11 位或 29 位标识符、
载荷长度，并拒绝错误帧和远程请求帧。

`LibusbTransport` 使用 Vendor Bulk 和 `RBU1` 长度帧头；`MockUsbTransport`
使用 Unix 字节流验证拆包与粘包。三者均已由 toolbusd 和 Mock MCU 端到端测试，
协议层仍不依赖 CAN 或 USB 类型。USB 细节见 [USB Vendor Bulk 传输](usb-transport.md)。

## 第四步：Mock MCU 远程核心

远程核心接收已经完成协议校验和重组的完整请求包，并生成完整响应包。它不直接
访问 CAN，也不包含任何设备专用驱动。

当前支持：

- `GET_INFO`：返回 UUID、三段式固件版本、板卡类型和协议版本。
- `GET_CAPABILITY`：返回 64 位通用硬件能力位图。
- `PING`：原样回显请求载荷。

所有响应载荷的第一个字节都是状态码。非成功响应同时设置响应头的错误标志。
响应会保留请求中的命令、会话 ID、请求 ID 和对象 ID，供主机准确匹配请求。

Mock MCU 进程通过后续各节描述的收发循环、心跳和发现机制接入 SocketCAN。

## 第五步：Mock MCU 收发流水线

`MockNode` 把已经实现的各层连接起来：

```text
CAN 载荷 -> 分片重组 -> 协议解码 -> RemoteCore
         -> 协议编码 -> 响应分片 -> CAN 载荷
```

独立的 `mock_mcu` 进程通过 `SocketCanTransport` 连接指定接口，支持
`classical` 和 `fd` 两种模式。广播发现与节点分配使用标准 CAN ID `0x700`。
节点 N 分配地址后，使用 `0x600 + N` 接收业务请求、`0x580 + N` 返回响应、
`0x500 + N` 每 500 ms 发送心跳。未分配节点使用由 Mock 实例号确定的临时
响应 CAN ID，避免多节点发现响应在分片重组时互相污染。SIGINT 或 SIGTERM
会让进程正常退出。

分片、协议和远程核心仍可完全脱离 SocketCAN 进行内存测试。这样即使开发环境
暂时没有 `vcan` 内核模块，也可以验证完整请求与响应流水线。

## 第六步：toolbusd 请求管理器

请求管理器负责为每个会话分配非零请求 ID，并保存等待响应的请求。收到响应时
同时校验会话 ID、请求 ID、命令和对象 ID，避免错误匹配。

每个请求具有独立的超时和剩余重试次数。到达截止时间后，请求管理器生成重试
事件；重试次数耗尽后生成超时事件。重试沿用原请求 ID，使远端节点可以根据
请求 ID 返回缓存结果，而不是再次执行带副作用的操作。

默认单次等待 750 ms。500 kbit/s Classical CAN + SLCAN 上，2048 字节请求和
响应的实测往返接近 450 ms；Bluepill 提升到 1 Mbit/s、SLCAN 端口参数提升到
2 Mbaud 后，最大载荷 PING 实测约 364 ms。750 ms 能覆盖最大合法数据包，并为
调度、总线竞争和较慢适配器保留余量，避免响应仍在重组时过早启动重试。

已经完成或超时的请求会在短时间内保留标识，用于识别迟到或重复响应。该核心
组件不直接访问 SocketCAN，后续由 `toolbusd` 事件循环负责发送重试帧和向本地
IPC 客户端投递最终结果。

## 第七步：远端重复请求缓存

Mock 节点以“会话 ID + 请求 ID”为缓存键，保存已经执行请求的完整内容和编码后
的响应。收到内容完全一致的重试时，节点使用新的或原有分片传输 ID 重新发送
缓存响应，不再次调用远程核心。

如果相同缓存键对应的命令、对象、标志或载荷不同，节点将其视为协议冲突并
拒绝执行。缓存容量固定，达到上限后按最早插入顺序淘汰；会话结束时可以显式
清除该会话的缓存。这样未来的 `GPIO_WRITE` 等带副作用操作也不会因响应丢失
和主机重试而执行两次。

## 第八步：节点发现和心跳

`DISCOVERY_REQUEST` 载荷包含主机支持的最低和最高协议版本。版本兼容的节点
返回 `DISCOVERY_RESPONSE`，其中包含 UUID、固件版本、板卡类型和协议版本。
不兼容节点保持静默。

主机使用 UUID 定向发送 `NODE_ASSIGN`，载荷包含 UUID 和非零节点 ID。只有
UUID 完全匹配的节点接受分配并返回确认，后续心跳在对象 ID 字段携带已分配的
节点 ID。

`NodeRegistry` 以 UUID 保存节点信息。发现响应会新增或刷新节点，心跳更新
最后在线时间。默认超过 2 秒没有心跳就将节点标记为离线；后续再次收到有效
发现响应或心跳时可以恢复在线状态。

## 第九步：远程 GPIO

GPIO 被划分为两个严格分离的部分：

- `RemoteCore` 管理远程对象 ID、协议校验和命令分发。
- `GpioBsp` 只提供配置、读取和写入三个原子硬件操作。

`GPIO_CREATE` 请求载荷固定为 4 字节：16 位小端引脚号、方向和初始电平。
成功响应在协议头的对象 ID 字段返回新对象 ID。`GPIO_READ` 使用对象 ID 且
请求载荷为空，成功响应载荷为状态码和一个电平字节。`GPIO_WRITE` 使用对象
ID，并携带一个取值为 0 或 1 的电平字节。

Mock BSP 保存模拟引脚状态并记录原子操作调用次数。相同会话 ID 和请求 ID 的
重复 `GPIO_WRITE` 由节点缓存直接返回响应，因此 BSP 写操作只执行一次。

## 第十步：完整本地通信链路

`toolbusd` 使用独立线程接收 CAN 帧、重组协议包、处理发现与心跳，并驱动请求
管理器的重试和超时。应用程序通过 Unix Domain Socket 提交完整协议请求，
不能直接访问 CAN。

当前本地 IPC 使用长度前缀帧。请求体是完整编码 Remote Packet；响应包含 IPC
状态、长度和响应包或错误文本。守护进程负责覆盖客户端请求 ID、发送分片、
匹配响应，并在重试耗尽后向客户端报告超时。

`remote-cli` 提供 `ping`、信息查询、能力查询和 GPIO 命令。进程级测试会同时
启动 `mock_mcu`、`toolbusd` 和 `remote-cli`，分别通过 Classical CAN 和
CAN-FD 验证以下真实路径：

```text
remote-cli -> Unix Domain Socket -> toolbusd
           -> vcan0 -> mock_mcu -> vcan0 -> toolbusd
           -> Unix Domain Socket -> remote-cli
```

## 第十一步：远程 UART

UART 同样分为远程对象管理和原子 BSP 操作。`UART_CREATE` 的固定 8 字节载荷
依次包含端口号、32 位小端波特率、数据位、停止位和奇偶校验。当前允许 5～8
数据位、1～2 停止位，以及无、奇、偶三种校验方式。

`UART_WRITE` 使用对象 ID，载荷就是需要发送的原始字节；成功表示整段数据已经
交给 BSP。`UART_READ` 使用对象 ID，并用 16 位小端整数指定本次最多读取的
字节数；响应在状态码后返回当前可用数据，不阻塞等待指定长度。

`UART_READ` 会消费 MCU 接收缓冲区中的数据，因此它与普通只读查询不同：
响应必须完整保存在节点的请求去重缓存中。单次最大读取长度为
`REMOTE_CACHE_RESPONSE_SIZE - 24 - 1`，其中 24 是协议头，1 是响应状态码。
当前 STM32 默认去重缓存为 256 字节，所以单次最多读取 231 字节。更长的数据
由 Linux 侧连续读取；重试仍使用相同请求 ID，从缓存返回同一批字节，不会把
下一批数据误当作前一次响应。

STM32F103 的 UART 0 已实现为 USART1 中断适配器。RX 和 TX 分别使用固定大小
环形缓冲，ISR 只搬运原始字节，不解析 Modbus、GPS 或厂商协议。`UART_WRITE`
先检查 TX 剩余空间，只有整段都能进入缓冲才返回成功；这样不会在资源紧张时
向外设发送半条协议报文。USART1 引脚可以在 menuconfig 中选择
PA9/PA10 或重映射后的 PB6/PB7。

Mock UART 后端提供接收数据注入、发送数据提取和原子调用计数。重复
`UART_WRITE` 由节点请求缓存响应，底层写操作只执行一次。它不实现 Modbus、
AT 命令或任何厂商设备协议。

## 第十二步：资源目录与资源级健康状态

能力位图只回答“板卡是否具备某类能力”，资源目录进一步列出每个可调度实例。
资源描述包含稳定资源 ID、资源类型、逻辑实例号、原生/扩展标志，以及收发缓冲
容量。Linux 不需要知道扩展 UART 背后是哪个 SPI 转串口芯片。

当前定义三个查询命令：

- `RESOURCE_ENUM`：返回板卡全部可分配资源。
- `RESOURCE_DESCRIBE`：按资源 ID 返回一项完整描述。
- `RESOURCE_STATUS`：返回单项资源的健康状态和错误标志。

Mock 工具板暴露 16 路 GPIO 和 8 路 UART。UART 0～3 为 MCU 原生接口，
UART 4～7 为板级扩展接口；8 路串口都声明 4096 字节收发缓冲。扩展芯片占用
的内部 SPI 不对 Linux 暴露，避免同一物理资源被重复分配。

`toolbusd` 可并发服务多个本地 IPC 客户端，请求仍由统一请求管理器分配 ID 和
匹配响应。每个客户端套接字设置读写超时，停止守护进程时会等待正在处理的
客户端退出，避免空闲连接无限阻塞关闭过程。

资源状态还包含当前 RX/TX 缓冲占用和收发溢出计数。缓冲达到 75% 时资源进入
忙状态；发生溢出后进入性能下降状态；后端异常时仅对应资源进入故障状态。
`RESOURCE_RESET` 可以清空单个 UART 的缓冲、溢出计数和故障锁存，不重启节点，
也不影响其他 UART。

## 第十三步：多节点寻址与公共客户端库

本地 IPC 请求显式携带目标节点 ID。`toolbusd` 会确认节点在线，并把请求发送到
该节点专用 CAN ID；响应除协议字段匹配外，还必须来自预期节点的 CAN ID。
因此一个节点不能错误地完成另一个节点的请求。

`libremotebsp` 提供线程安全的同步 C++ API，包括节点列表、信息/能力查询、
资源查询与复位、GPIO、UART、PWM、定时位流/WS2812和运动段/状态/停机。
每次调用使用独立 UDS 连接，一个慢调用不会污染
其他线程的响应流。`toolbusd` 每次启动生成新的非零会话 ID，并覆盖客户端提供
的会话值，避免守护进程重启后请求 ID 与 MCU 旧去重缓存冲突。

节点 ID 分配采用“心跳确认”语义：`toolbusd` 发出 `NODE_ASSIGN` 后，在收到携带
该节点 ID 的心跳之前都保持未确认状态。后续发现响应会触发同一节点 ID 的幂等
重发，避免单帧或响应丢失后节点永久停在待分配状态，也不会因重试消耗新的 ID。

双节点端到端测试会在同一 `vcan0` 上启动两个 Mock MCU，验证节点寻址、同编号
GPIO 状态隔离，以及一个节点离线 2 秒后另一个节点继续服务。Classical CAN 和
CAN-FD 都执行该测试。

## 第十四步：异步事件通路

远端事件使用协议的 `Event` 消息类型。UART RX 事件命令为
`UART_RX_EVENT`，对象 ID 字段携带逻辑 UART 资源 ID，载荷保持为未经解析的
原始字节。Modbus、GPS NMEA 或其他设备协议仍由 Linux 应用处理。

`toolbusd` 按节点保存最多 256 条待取事件，队列满时淘汰最旧事件，避免异常数据
源造成无限内存增长。`libremotebsp::Client::next_event()` 使用最长 1 秒的
阻塞等待获取下一条事件；不同节点使用独立队列。Mock MCU 的
`--uart-stream` 选项用于端到端生成 UART 7 测试流。

当前事件通路已经解决持续数据不必反复发送 `UART_READ` 的问题。每资源带宽
配额、事件优先级和溢出丢弃计数公开仍需后续增强。

## 第十五步：Katapult 双模式升级

STM32 APP 支持 `BOOTLOADER_ENTER` 和 `BOOTLOADER_ENTER_USB` 两个原子命令，
分别选择 CAN 和 USB Katapult。载荷必须是固定 8 字节确认串，节点先缓存并
发送成功响应，再延迟约 100 ms 写入对应的 Katapult RAM 请求签名并复位。
相同会话 ID 和请求 ID 的重试只返回缓存响应，不能重复执行复位副作用。

Flash 前 8 KiB 分配给 Katapult，APP 和其中断向量表从 `0x08002000` 开始。
首次烧录使用 Bootloader+APP 合并镜像，后续在线升级只传输带偏移链接的 APP
镜像。Katapult 作为 GPLv3 独立程序构建，不与 RemoteBSP APP 静态链接。
F103 和 G431 使用同一套双模式补丁：APP 命令可以选择 CAN 或 USB，复位时
按住 PA0 或 APP 无效也会选择 USB 应急恢复。两个通信后端同时链接，但运行时
只初始化一个；F103 因而不会同时启用共享专用 SRAM 的 USB 与 bxCAN。

正式板卡预设默认仍通过 CAN/CAN-FD 承载业务、遥测和诊断。G431 另提供互斥的
USB Vendor Bulk APP 预设，已经具备 Linux、Mock、MCU 公共帧格式和 USB Device
后端并通过交叉编译，实体枚举与压力测试待验收。Katapult USB 仍是独立程序和
独立 PID。详细构建、升级和安全边界见
[Katapult 双模式升级与应急恢复](bootloader-upgrade.md)。

## 第十六步：资源能力合同与会话级租约

资源描述回答“这是什么资源”，能力合同进一步回答“当前配置可以保证什么”。
Mock MCU 已实现`RESOURCE_CONTRACT`，固定32字节合同包含：

- 资源ID、合同版本和读写/共享/独占/租约能力标志。
- 定时分辨率和最坏操作延迟。
- 最大每秒操作数和队列容量。
- 最大RX/TX位速率。

数值为0表示不适用或尚未声明，不表示无限能力。Mock数值用于协议和准入流程
验证；F103/G431的正式保证值必须来自后续实体压力测试。

资源租约命令包括：

```text
RESOURCE_ACQUIRE
RESOURCE_RENEW
RESOURCE_RELEASE
RESOURCE_LEASE_STATUS
```

当前允许100～60000 ms租期，支持共享读和独占两种模式。节点拒绝冲突租约，
续租和释放必须匹配资源ID、会话ID与64位租约ID。独占租约下创建的GPIO/UART
对象绑定远端会话；其他远端会话不能操作该对象。租约到期、显式释放或会话清理
时，Mock会删除关联对象，将GPIO输出拉低并复位UART缓冲，随后资源才能被新
会话取得。重复请求仍由现有请求缓存保证幂等。

为兼容当前稳定API，没有活动租约且合同未声明“强制租约”时，旧GPIO/UART命令
仍可工作。当前`toolbusd`给所有短连接本地调用使用同一个远端会话，所以这一步
已经能隔离不同远端主机/守护进程，但尚不能形成不可绕过的Linux本地应用身份。
本地强所有权需要持久IPC客户端身份，或让每次受保护操作显式携带租约令牌。

## 第十七步：统一板卡描述与数字孪生

Mock不再在进程入口硬编码资源数量和合同。`boards/mock-generic-v1.json`作为
版本化事实来源，声明板型、UUID模板、固件版本、能力、公开资源、能力合同和
内部保留资源。严格加载器在节点启动前检查schema、字段、数值范围、能力匹配、
重复资源以及公开/内部占用冲突。

板型和节点身份分离：同型号节点使用同一`board_type`，不同Mock实例通过UUID
最后一个字节区分。扩展UART组占用的SPI记录为内部保留项，不进入远程资源枚举，
Linux看到的是与原生UART使用相同接口的逻辑串口。

数字孪生在相同资源目录之上执行按单调相对时间排序的故障事件。当前支持单路
UART故障/恢复、GPIO外部输入和节点离线/恢复。资源级故障只改变目标资源，
节点级离线才停止心跳、响应和异步事件。测试可直接推进虚拟毫秒位置，不需要
实际等待，从而重复验证相同的状态转换顺序。详细格式见
[统一板卡描述与数字孪生 Mock](board-manifest-and-digital-twin.md)。

## 第十八步：CAN业务分类与带宽准入

`toolbusd`发送前先完成远程包编码和分片，再按每个实际CAN帧计算保守线时间。
Classical CAN使用11位标准数据帧基础长度，并加入最坏位填充上界；CAN-FD先按
控制器支持的DLC向8、12、16、20、24、32、48或64字节补齐，再分别计算仲裁
段和BRS数据段时间。配置的位速率必须与SocketCAN接口一致。

当前业务分为安全、运动、系统、交互、持续流和大块传输六类。全局令牌桶限制
总发送利用率，每类令牌桶限制该类突发量。普通IPC请求预算不足时在任何CAN帧
发送前拒绝，并取消尚未发送的请求管理器条目；重试、节点分配和未来安全命令
使用保证发送路径，预算不足时仍发送并增加`guaranteed_overruns`计数。

CAN-FD消息已在传输接口中显式携带BRS属性，SocketCAN编码设置`CANFD_BRS`；
vcan端到端测试同时检查FDF和BRS标志。`traffic-status`通过本地IPC公开当前
速率、突发窗口、可用全局预算以及各业务类的累计准入、拒绝、帧数和估算线
时间。

本阶段是准入控制，不是完整调度器。发送仍以进入`send_packet`的先后顺序串行
执行，尚不能让后到达的安全消息抢占已经开始发送的大包。下一阶段需要将远程包
进入有界优先级队列，按节点和资源设置配额，并对运动组执行显式带宽预留。

## 智能实时资源层

多轴步进控制不会实现为经 CAN 逐次翻转 GPIO。Linux 将轨迹转换为带绝对执行
时间的压缩运动段，MCU 使用共同定时器基准驱动 STEP/DIR/EN，并在本地处理
限位和急停。TMC 型号、寄存器含义和初始化仍属于 Linux；MCU 只提供通用
UART、半双工 UART 和 SPI 原子事务。

编译期配置与运行时接线配置严格分离。`menuconfig` 负责 MCU、晶振、CAN、
USB、Bootloader 以及是否链接运动/输入/总线模块；轴引脚、限位、TMC 总线和
资源依赖保存为带版本、CRC 和 A/B 原子提交的非易失资源清单。详细的队列模型、
安全状态、资源占用和分阶段实现要求见
[智能实时资源与多轴运动控制设计](intelligent-motion-resources.md)。

不同板卡上的轴使用 64 位全局运动时间。`toolbusd` 分别估计每块 MCU 的时钟
偏移和漂移，运动段提前装入所有节点；全部节点报告就绪后，再提交同一个未来
绝对开始时间。同步不依赖 CAN 包恰好同时到达。任一节点在提交前未就绪，整组
取消；时钟误差或队列余量越界时，按共同段边界停止。跨板限位仍受总线延迟影响，
不能替代同板联锁或硬件急停线。

Mock第一阶段已经实现板卡能力驱动的多轴运动段入队、共同时间轴STEP/DIR/EN边沿、有界队列、
限位/欠载/主动停止安全状态和运动遥测。`MOTION_ENQUEUE`/`MOTION_STATUS`归入
运动业务预算，`MOTION_ABORT`走不因软件预算耗尽而拒绝的保证发送安全路径。当前段内
使用均匀步间隔；跨板时钟同步、准备/提交事务和STM32定时器后端仍未实现。

轴数不是全系统常量。当前协议为单节点状态报文设置64轴的有界上限，各节点根据
MCU、定时器和中断预算公开更小的实际保证值。逻辑运动组可以跨节点组合，主机
把轨迹拆成节点本地段并提交同一个全局开始时间；因此整机总轴数不受单节点上限
约束。
